# How I used Kiro to build Decay Engine

Decay Engine is one engine for things that fade, with two apps on top: Study Dungeon (facts you are forgetting) and Ghosted (friendships going quiet). The engine has a small policy contract, and each app supplies its own decay rules and its own look. Ghosted is the reuse proof. Everything below comes from `docs/KIRO_LOG.md`, a session-by-session record I kept while building. I also used Claude Code (Anthropic's coding agent) outside Kiro for part of the work. This write-up says exactly which parts in the last section, and the log and `.kiro/steering/authorship.md` list the files.

## Kiro built most of this project

- **2,650 Kiro credits** (2,649.91 of the 4,000 hackathon credits, from Kiro's usage panel on Nov 24) over 75 logged sessions. The log itemises about 2,345. The other 305 or so are IDE sessions with no recorded figure (19, 38, 42, 44, 46, 60 and the build part of 45); the panel only gives a running total, so that amount is not split between them.
- **Three full specs** (engine, Study Dungeon, Ghosted), about 7,700 lines of requirements, design and tasks when first approved, all generated by Kiro and reviewed by me stage by stage. Kiro later extended the two app specs with three more features (Sessions 44, 46 and 58).
- **About three-quarters of the code, at most.** On Nov 21 the repo had about 49,600 lines of TypeScript, TSX and CSS, and Kiro had written about 36,600 of them (about 74%; an upper bound, because Claude Code also edited some Kiro-written files and I cannot split those lines): the engine modules, the whole shared shell, almost all of Ghosted, most of Study Dungeon's screens, and most of the tests. I have not recounted since Sessions 42 to 59 and the outside-Kiro fixes listed at the end.
- **2,672 tests** across five packages at the last full run on Nov 24 (engine 701, shell 166, Study Dungeon 743, Ghosted 988, insight 74). Kiro wrote most of them, including every app policy test and Ghosted's property suites. Kiro could not run commands in its build sessions, so the tests it wrote in Sessions 59, 61 and 64 were first run by Claude Code, which found and fixed one shell test file that did not load and one insight test that called `replay` without the `until` its own assertion needed.
- **Steering files, three hooks, one custom agent and two MCP servers (Context7 and Playwright)**, all in `.kiro/`.

About 12,900 lines (about 26%) were written by Claude Code, outside Kiro, at my request (see the last section). That includes the decay-rule code and a few core algorithms, by design: I specified the rules and chose to have a second tool write that code. It was a choice about who owns the rules, not a gap in what Kiro could do: for Ghosted I let Kiro write the policy too, from formulas I had fixed in the spec.

## Which Kiro apps I used

I used the **Kiro IDE** for the whole build and added **Kiro CLI** near the end (Session 39). I did not use Kiro Web or Kiro Crew.

**IDE vs CLI.** The CLI runs inside WSL, where the project lives. The same `policy-reviewer` agent file loaded in both without changes. In the IDE (Session 36) I had to run the agent's tests myself and paste the results back. In the CLI the agent ran `policy.test.ts` (44 of 44) and `policy.properties.test.ts` (9 of 9) itself, for 1.74 credits. The CLI chat also handed the review to the agent as a sub-agent instead of starting a second session.

I tried the Linux build of Kiro inside WSL (Session 12) to fix a problem, described next, and dropped it. Kiro's shell tool was unreliable on my setup (Kiro runs on Windows, the project lives in WSL). That shaped the workflow: **Kiro wrote the files, and I ran each test and typecheck in WSL and pasted the results back.** Kiro marked a task done only after a passing run. This kept every claim in the log checked.

**Build in the IDE, measure from the CLI (Sessions 43 to 59).** For the last features I split the work by app. In the IDE, Kiro built spec tasks with file edits only, and its prompts forbade commands. Kiro CLI then ran the checks and used the Playwright MCP to measure the result in a browser at 1280×800, 390×844 and 320×640. When a measurement failed, the CLI was told to stop and report, not fix. A CSS change followed (by Claude Code, outside Kiro), and the CLI measured again. The Ghosted dock went through four rounds like this (Sessions 47 to 49 and the outside-Kiro fixes between them).

## Spec-driven development (the core of the build)

I built three specs the same way: requirements, design, tasks, with a review stop after each step. Kiro then implemented the tasks one round at a time.

| Spec | Result |
|---|---|
| Engine | 18 requirements, about 2,300 lines of design, 37 tasks |
| Study Dungeon | 18 requirements, 20 tasks (58 with sub-tasks), built in 7 Kiro rounds (about 362 credits) |
| Ghosted | 32 requirements, 13 correctness properties, tasks grouped A to F, built in Sessions 20 to 37 (about 790 credits) |

**What the spec approach did for me, compared with vibe coding.** Reviewing the spec text caught bugs before any code existed. Examples from the log:

- **Death redefined.** Kiro's first requirements redefined "dead" as "health reaches 0" in four places, contradicting the threshold rule in the same file.
- **Double decay.** Kiro's `tick` saved new health without saying what happens to `lastEventAt`, which would make a time-based policy decay an item twice. This became a rule plus a property test ("splitting time makes no difference").
- **A feature described and never used.** Kiro's first design wrote the death-time bisection as its own module, but `settle` still stamped every death with "now". Autopsy would have reported the wrong day after any long absence.
- **Preview mode that never worked.** The Study Dungeon design detected preview by comparing `now` with `Date.now()`, which changes every millisecond, so the app would have blocked every action.
- **A requirement quietly dropped.** The task list skipped the shared `packages/shell`. Kiro read "build only what Study Dungeon needs" as "don't build the shell yet".
- **A float bug found by Kiro.** While drafting Ghosted's requirements, Kiro noticed that `100 × (1 − elapsed / T)` gives 9.999999999999998 on day 81, so a person would die a day early. The form `100 × (T − elapsed) / T` gives exactly 10.

**Reuse through specs.** The Ghosted spec reused the engine contract unchanged. Kiro extended the shared shell (time machine range and jumps, Triage budget choices, autopsy markers) in small tasks (Sessions 22 to 24, about 31 credits together), and Study Dungeon kept working on the same shell.

**Late features through the same specs.** Each was written by Kiro as requirements, design and tasks before any code: a compact time dock (L2, Session 44), a line under each hero saying what is lost in the next 7 days if nothing is done (P4, Session 46), a Triage line saying how many picks this session saves (P5, Session 58), a small package, `@decay-engine/insight`, that replays an item's history and answers "what if" (E1, Session 62), a Rescue Point line in each autopsy built on it (R1, Session 65), live state changes while the tab is open (L3, Session 69), opt-in notifications (L5, Session 71) and a first-look intro that plays the time machine once (L6, Session 73). Each build was followed by a browser check from Kiro CLI that measured and stopped on failure (Sessions 47 to 75). Writing them as specs first surfaced decisions I had to make, for example:

- "in the next 7 days" instead of "this week", because the window is a rolling 7 days, not a calendar week;
- whether an item that dies exactly at day 7 counts (it does, because the dock marks it on day 7);
- that P5 needs one optional shell prop (`picksNote`), because the Triage panel keeps its picks in its own state and no app-only change can reach them. The prop was added to the shell's allow-list in `scripts/check-engine-unchanged.sh`.

While building P4, Kiro found a case the design had left open: a person at exactly health 60 is due "now", gets no marker, and is still fading a week later. It wrote a narrow carve-out in Property 14 with a unit test pinning the case, and flagged it instead of hiding it.

**The engine never changed.** In Session 42 Kiro rewrote `scripts/check-engine-unchanged.sh` against a tag, `engine-complete`, set before either app was built. A file passes only if every changed line is a whole-line comment. Kiro checked the script in a throwaway worktree: a changed constant, a trailing comment after code and a new untracked file each fail, and HEAD passes.

**What I learned about cost.** The requirements step was usually close, and small targeted corrections cost about 2 credits each. Design and tasks cost about seven times more and held the worst bugs. Large rewrites through Kiro were expensive (11 credits to rewrite one test section), so I asked for targeted edits instead.

## Steering

Ten steering files in `.kiro/steering/`. The ones that changed Kiro's behaviour most:

- **`engine-boundary.md`** forbids the engine from reading a clock, touching the browser (outside one adapter), importing an app, or having runtime dependencies. The rule became a test: boundary tests read the source and fail on any violation. I confirmed this by adding a file that broke all three rules, and all three checks failed.
- **`no-fake-tests.md`** came from studying last year's RumorNet, whose author wrote about AI tests that pass without checking anything. It forbids catching errors to pass, weakening tests, or editing expected values to match wrong output.
- **`authorship.md`** tells Kiro which files were written outside Kiro and must not be rewritten, so Kiro never overwrote the decay rules, and it records which tool wrote what.
- **`shell-commands.md`** (Session 44) came from repeated shell trouble: commands that printed nothing, polling loops, and two cancelled runs. Its rules: one command per call, long output to a file, long work in the background, stop after two identical failures, never start a server, never change git config. The last rule exists because in Session 42 Kiro ran `git config --global core.pager cat` without asking to escape a stuck pager (it noticed and unset it straight away). After the file was added, every command output in that session was readable.
- **Two steering mistakes, as a lesson.** In its first update (Session 5), Kiro invented a different policy contract instead of reading the engine spec. Later (Session 9), a stale async `resurrect` signature that I had missed in three steering files made Kiro stop and ask before writing `types.ts`. Steering is loaded into every prompt, so a wrong line costs more than a wrong line in a spec. Prompts now name the files that are the source of truth.

## Hooks

I defined three hooks. This was my weakest Kiro feature:

- **Scaffold a new decay policy.** On a prompt like "scaffold the policy for X", Kiro creates the starter policy, skin and `it.todo` test stubs, without writing any decay rules. The matcher is not documented for prompt hooks, so it fired on every prompt until I added a gate to its instructions. Kiro used it to scaffold Ghosted.
- **Check a policy on save.** Runs an app's policy tests and `checkPolicy` when `policy.ts` is saved, and reports in words without editing the policy. Kiro's docs say file hooks fire only on agent edits. In Session 37 an agent edit did **not** fire it. In Session 38 I repeated the same test and it fired twice (once for the edit, once for the revert), and Kiro ran the 44 policy tests both times. Between the two tests I also changed the matcher to accept either slash direction. The event's path used forward slashes, so the old matcher would have matched too. I don't know why it failed the first time.
- **Run engine tests on save.** A file-save command hook. Its command depends on Kiro's shell, which was unreliable on my setup, so I have not seen it deliver results yet.

## Custom agent

`policy-reviewer` (`.kiro/agents/policy-reviewer.md`) is read-only. It has `read` and `shell` tools only, a permission rule allowing only the policy test command, and the steering files attached as resources. It reviews an app's `policy.ts` against the engine contract and the project rules, and reports in words.

On its first run it found a real conflict: Study Dungeon's requirement 4.1 and its design disagreed about what a successful resurrect returns. I had fixed the design by hand earlier and never updated the requirement. On Ghosted's Kiro-written policy it checked contract, purity and tests (44 passing) and flagged one minor issue, `nextDueAt` using the numbers 60 and 10 instead of reading the thresholds. I accepted it. Using one Kiro agent to review another Kiro session's code gave me a second reader with a clean context.

## MCP

One server is configured: **Context7** (`.kiro/settings/mcp.json`), which gives Kiro current docs for React, Vite and fast-check. The concrete use I logged: Kiro used it to check that Vite applies the tsconfig `jsx` setting to the shell's `.tsx` tests without the React plugin (Session 14). I also corrected its auto-approve list by hand, because Context7 had renamed its docs tool to `query-docs`.

It is a documentation server. It saved guesswork about library APIs, and it did not unlock a workflow that would otherwise have been impossible.

The second server, **Playwright MCP** (`@playwright/mcp`), did real work. From Kiro CLI it opened both live Netlify sites in headless Chromium, loaded sample data, moved the time machine 30 days ahead, ran Triage for 20 minutes, and saved six screenshots (Session 41). Kiro looked at each screenshot after saving it and retook two that were wrong (a tour popup covering the time machine, and Triage still set to 30 minutes). Getting there took one fix: the default Chrome browser needed `sudo` to install, so I switched the server to Chromium. The same install attempt also deleted two Playwright downloads from my cache without warning; Kiro told me right after, and nothing in the repo was affected.

After that, Playwright became the main way to check layout, which jsdom cannot measure. From Kiro CLI it measured element boxes at three screen sizes and found failures no unit test had caught:

- At 390×844 the first row of Ghosted windows ended 21px under the time dock, so the state labels were hidden (Session 43). The first reading compared the row with the screen height only and said it passed; the screenshot showed the dock covering it.
- The expanded Ghosted dock hid Play and three of the four jumps behind a sideways scroll at 390 and 320px (Session 47), and then "Back to today" sat below the screen while previewing (Session 48).
- After the 7-day loss line was added, the first row of windows was again 48.7px behind the dock at 390×844, and the line touched the hero buttons with a 0px gap (Session 51).
- In Study Dungeon's expanded dock at 320×640, Play was clipped by 2.5px (Session 54).

Each of these was fixed and measured again until it passed, except one: at 320×640 Ghosted's hero and dock together leave no room for the first row of windows (Session 52). That is recorded as open.

## Property-based testing

fast-check property suites cover the engine (17 properties, at least 100 runs each) and Ghosted's policy, window, card and write guard. Kiro wrote the Ghosted suites from the 13 correctness properties in the Ghosted design. They check rules such as "splitting time makes no difference", "health never increases between events", and "an item dead at `now` was already dead at its `diedAt` and not a minute earlier".

**What PBT caught and what it did not.**

- **Design review of the PBT plan.** The first generators made nearly every item die immediately, so the properties would have passed while checking almost nothing. This led to a generator coverage check (alive, weak and dead items each at least 10%), which every app now runs.
- **A gap, found by breaking the code on purpose.** I made bisection return the early end of its final minute, and all 17 properties still passed. I added a property for it, and now that change fails a test.
- **A rare seed, found by repeating the run.** Kiro's Study Dungeon property for the Rescue Point line passed on its first run and failed on about one run in four. The shrunk counterexample was a fact whose first answer is wrong at the moment it is created: it is weak from creation, and the insight package rejects a what-if at the creation time, so there is correctly no line. The property had not excluded that case. It now asserts "no line" for it (Claude Code, outside Kiro). Running each new property file a dozen times, not once, is how it surfaced.
- **No bug in an app policy.** When I broke Ghosted's policy nine ways to test the tests, eight were caught. The ninth was an equivalent mutant. No property found a real bug in the policy.

## Kiro powers

I used the **`netlify-deployment`** power for the deploy (Session 40). Its guide set the plan: one `netlify.toml` per app, the Netlify CLI rather than the web UI, and a draft deploy before production. Kiro wrote both configs in the IDE, and Kiro CLI created the two sites and ran the draft deploys. One catch: I installed the power in the IDE, and the CLI could not find it by name, so the power's guidance came through the IDE session.

## Who wrote what

I own the decay rules. Every formula and threshold is set in the specs. For Study Dungeon, I had Claude Code write the policy code from those specs, outside Kiro. For Ghosted, Kiro wrote the policy from the formulas and the `policy-reviewer` agent checked it. Claude Code also ran the tests and the deliberate break-the-code checks in WSL during the engine and Study Dungeon sessions (Sessions 9 to 18), because Kiro's IDE shell could not run commands on my setup. ## What I would tell another builder

1. Review every spec stage. Kiro's summary said "everything matched" when it had invented a policy contract.
2. Break your own code on purpose. A passing suite proves little until a deliberate bug makes it fail.
3. If Kiro's shell does not work on your setup, let it write files and run the checks yourself. You lose some automation and keep control.
4. Keep building and measuring apart. A run told to measure and stop on failure gave me numbers I could trust; even in runs told not to use the shell, Kiro still made harmless no-op shell calls (`echo skip`, `true`) and reported them.
