# How I used Kiro to build Decay Engine

Decay Engine is one engine for things that fade, with two apps on top: Study Dungeon (facts you are forgetting) and Ghosted (friendships going quiet). The engine has a small policy contract, and each app supplies its own decay rules and its own look. Everything below comes from `docs/KIRO_LOG.md`, a session-by-session record I kept while building.

## Kiro built most of this project

- **About 1,500 Kiro credits** over 37 logged sessions (1,363 on Kiro's usage panel on Nov 21, itemised session by session in the log).
- **Three full specs** (engine, Study Dungeon, Ghosted), about 7,700 lines of requirements, design and tasks, all generated by Kiro and reviewed by me stage by stage.
- **About three-quarters of the code.** The repo has about 49,600 lines of TypeScript, TSX and CSS. Kiro wrote about 36,600 of them: the engine modules, the whole shared shell, almost all of Ghosted, most of Study Dungeon's screens, and most of the tests.
- **1,983 tests** across four packages (engine 701, shell 152, Study Dungeon 465, Ghosted 665). Kiro wrote most of them, including every app policy test and Ghosted's property suites.
- **Ten steering files, three hooks, one custom agent and two MCP servers (Context7 and Playwright)**, all in `.kiro/`.

The parts I wrote myself are the decay rules and a few core algorithms, by design (see the last section). That was a choice about who owns the rules, not a gap in what Kiro could do: for Ghosted I let Kiro write the policy too, from formulas I had fixed in the spec.

## Which Kiro apps I used

I used the **Kiro IDE** for the whole build and added **Kiro CLI** near the end (Session 39). I did not use Kiro Web or Kiro Crew.

**IDE vs CLI.** The CLI runs inside WSL, where the project lives. The same `policy-reviewer` agent file loaded in both without changes. In the IDE (Session 36) I had to run the agent's tests myself and paste the results back. In the CLI the agent ran `policy.test.ts` (44 of 44) and `policy.properties.test.ts` (9 of 9) itself, for 1.74 credits. The CLI chat also handed the review to the agent as a sub-agent instead of starting a second session.

I tried the Linux build of Kiro inside WSL (Session 12) to fix a problem, described next, and dropped it. Kiro's shell tool was unreliable on my setup (Kiro runs on Windows, the project lives in WSL). That shaped the workflow: **Kiro wrote the files, and I ran each test and typecheck in WSL and pasted the results back.** Kiro marked a task done only after a passing run. This kept every claim in the log checked.

## Spec-driven development (the core of the build)

I built three specs the same way: requirements, design, tasks, with a review stop after each step. Kiro then implemented the tasks one round at a time.

| Spec | Result |
|---|---|
| Engine | 18 requirements, about 2,300 lines of design, 37 tasks |
| Study Dungeon | 18 requirements, 20 tasks (58 with sub-tasks), built in 7 Kiro rounds (about 362 credits) |
| Ghosted | 32 requirements, 13 correctness properties, tasks grouped A to F, built in Sessions 20 to 37 (about 790 credits) |

**What the spec approach did for me, compared with vibe coding.** Reviewing the spec text caught bugs before any code existed. Examples from the log:

- **Death redefined.** Kiro's first requirements redefined "dead" as "health reaches 0" in four places, contradicting the threshold rule in the same file.
- **Double decay.** Kiro's `tick` saved new health without saying what happens to `lastEventAt`, which would make a time-based policy decay an item twice. This became a rule plus a property test ("splitting time makes no difference").
- **A feature described and never used.** Kiro's first design wrote the death-time bisection as its own module, but `settle` still stamped every death with "now". Autopsy would have reported the wrong day after any long absence.
- **Preview mode that never worked.** The Study Dungeon design detected preview by comparing `now` with `Date.now()`, which changes every millisecond, so the app would have blocked every action.
- **A requirement quietly dropped.** The task list skipped the shared `packages/shell`. Kiro read "build only what Study Dungeon needs" as "don't build the shell yet".
- **A float bug found by Kiro.** While drafting Ghosted's requirements, Kiro noticed that `100 × (1 − elapsed / T)` gives 9.999999999999998 on day 81, so a person would die a day early. The form `100 × (T − elapsed) / T` gives exactly 10.

**Reuse through specs.** The Ghosted spec reused the engine contract unchanged. Kiro extended the shared shell (time machine range and jumps, Triage budget choices, autopsy markers) in small tasks (Sessions 22 to 24, about 31 credits together), and Study Dungeon kept working on the same shell.

**What I learned about cost.** The requirements step was usually close, and small targeted corrections cost about 2 credits each. Design and tasks cost about seven times more and held the worst bugs. Large rewrites through Kiro were expensive (11 credits to rewrite one test section), so I asked for targeted edits instead.

## Steering

Ten steering files in `.kiro/steering/`. The ones that changed Kiro's behaviour most:

- **`engine-boundary.md`** forbids the engine from reading a clock, touching the browser (outside one adapter), importing an app, or having runtime dependencies. The rule became a test: boundary tests read the source and fail on any violation. I confirmed this by adding a file that broke all three rules, and all three checks failed.
- **`no-fake-tests.md`** came from studying last year's RumorNet, whose author wrote about AI tests that pass without checking anything. It forbids catching errors to pass, weakening tests, or editing expected values to match wrong output.
- **`authorship.md`** tells Kiro which files are hand-written and must not be rewritten, so Kiro never overwrote the decay rules.
- **Two steering mistakes, as a lesson.** In its first update (Session 5), Kiro invented a different policy contract instead of reading the engine spec. Later (Session 9), a stale async `resurrect` signature that I had missed in three steering files made Kiro stop and ask before writing `types.ts`. Steering is loaded into every prompt, so a wrong line costs more than a wrong line in a spec. Prompts now name the files that are the source of truth.

## Hooks

I defined three hooks. This was my weakest Kiro feature:

- **Scaffold a new decay policy.** On a prompt like "scaffold the policy for X", Kiro creates the starter policy, skin and `it.todo` test stubs, without writing any decay rules. The matcher is not documented for prompt hooks, so it fired on every prompt until I added a gate to its instructions. Kiro used it to scaffold Ghosted.
- **Check a policy on save.** Runs an app's policy tests and `checkPolicy` when `policy.ts` is saved, and reports in words without editing the policy. Kiro's docs say file hooks fire only on agent edits. In Session 37 an agent edit did **not** fire it. In Session 38 I repeated the same test and it fired twice (once for the edit, once for the revert), and Kiro ran the 44 policy tests both times. Between the two tests I also changed the matcher to accept either slash direction. The event's path used forward slashes, so the old matcher would have matched too. I don't know why it failed the first time.
- **Run engine tests on save.** A file-save command hook. Its command depends on Kiro's shell, which was unreliable on my setup, so I have not seen it deliver results yet.

## Custom agent

`policy-reviewer` (`.kiro/agents/policy-reviewer.md`) is read-only. It has `read` and `shell` tools only, a permission rule allowing only the policy test command, and the steering files attached as resources. It reviews an app's `policy.ts` against the engine contract and the project rules, and reports in words.

On its first run it found a real conflict: Study Dungeon's requirement 4.1 and its design disagreed about what a successful resurrect returns. I had fixed the design by hand earlier and never updated the requirement. On Ghosted's Kiro-written policy it checked contract, purity and tests (44 passing) and flagged one minor issue, `nextDueAt` using the numbers 60 and 10 instead of reading the thresholds. I accepted it. Using one Kiro agent to review another Kiro session's code gave me a second reader with a clean context.

## MCP

One server is configured: **Context7** (`.kiro/settings/mcp.json`), which gives Kiro current docs for React, Vite and fast-check. The concrete use I logged: Kiro used it to check that Vite applies the tsconfig `jsx` setting to the shell's `.tsx` tests without the React plugin (Session 14). I also corrected its auto-approve list by hand, because Context7 had renamed its docs tool to `query-docs`.

It is a documentation server. It saved guesswork about library APIs, and it did not unlock a workflow that would otherwise have been impossible.

The second server, **Playwright MCP** (`@playwright/mcp`), did real work. From Kiro CLI it opened both live Netlify sites in headless Chromium, loaded sample data, moved the time machine 30 days ahead, ran Triage for 20 minutes, and saved six screenshots (Session 41). Kiro looked at each screenshot after saving it and retook two that were wrong (a tour popup covering the time machine, and Triage still set to 30 minutes). Getting there took one fix: the default Chrome browser needed `sudo` to install, so I switched the server to Chromium.

## Property-based testing

fast-check property suites cover the engine (17 properties, at least 100 runs each) and Ghosted's policy, window, card and write guard. Kiro wrote the Ghosted suites from the 13 correctness properties in the Ghosted design. They check rules such as "splitting time makes no difference", "health never increases between events", and "an item dead at `now` was already dead at its `diedAt` and not a minute earlier".

**What PBT caught and what it did not.**

- **Design review of the PBT plan.** The first generators made nearly every item die immediately, so the properties would have passed while checking almost nothing. This led to a generator coverage check (alive, weak and dead items each at least 10%), which every app now runs.
- **A gap, found by breaking the code on purpose.** I made bisection return the early end of its final minute, and all 17 properties still passed. I added a property for it, and now that change fails a test.
- **No bug in an app policy.** When I broke Ghosted's policy nine ways to test the tests, eight were caught. The ninth was an equivalent mutant. No property found a real bug in the policy.

## Kiro powers

I used the **`netlify-deployment`** power for the deploy (Session 40). Its guide set the plan: one `netlify.toml` per app, the Netlify CLI rather than the web UI, and a draft deploy before production. Kiro wrote both configs in the IDE, and Kiro CLI created the two sites and ran the draft deploys. One catch: I installed the power in the IDE, and the CLI could not find it by name, so the power's guidance came through the IDE session.

## Who wrote what

I own the decay rules. Every formula and threshold is set in the specs, and I wrote the Study Dungeon policy myself so that the rules are mine. For Ghosted, Kiro wrote the policy from those formulas and the `policy-reviewer` agent checked it.

| Engine modules: types, errors, state, settle, bisection, serialization, storage, checkPolicy, forecast | Kiro |
| Shared shell: hero, counters, item card, history, autopsy, Triage panel, time machine | Kiro |

## What I would tell another builder

1. Review every spec stage. Kiro's summary said "everything matched" when it had invented a policy contract.
2. Break your own code on purpose. A passing suite proves little until a deliberate bug makes it fail.
3. If Kiro's shell does not work on your setup, let it write files and run the checks yourself. You lose some automation and keep control.
